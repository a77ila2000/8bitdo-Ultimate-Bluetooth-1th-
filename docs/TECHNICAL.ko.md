# 수정 내용과 한계

앱 기준 주소는01018000, 원본 크기는104960바이트다. 컨트롤러 섹션은 version111/PID6007,
수신기는 version104/PID6008을 유지한다. [전체 전후 바이트](../patches/controller.json), [직접 작성한 페이로드](../patch_source.py).
최종 enhanced는105472바이트이며 DAT 헤더 포함105500바이트다.

## ADC·배터리 (최초 수정)

| 수정 | v1.11 위치 | 전후 |
|---|---|---|
| 다섯 번째 정상 샘플 분기 |0101eaba, 앱+6aba| `01e0` → `1ce0` (실제 바뀌는 바이트는1개) |
| 경고 카운터 갱신 |01023eec, 앱+beec|12바이트 교체: 기존 byte 전체 OR 대신 bit7 유지 + 새 low7 count |

정상 샘플은 기존 유효 범위 조건을 통과한 값이다. 전부 비정상인 경우 기존 ADC 재초기화·누적 복구를 보존한다.
다섯 번째 정상 샘플의 카운터는0→1이므로 그 사례만 반복해 재시작에 도달하지 않는다.
배터리 경고는 기존 high bit 래치를 유지하고 낮은7비트 카운터를 교체한다. 전압 임계값·실제 보호 회로를 변경하지 않는다.

## 2ms 계산

기존 setter0101e9e4는 `floor(C/200) * uint8(floor(p/5))`를 사용한다.
`p=2`만 넘기면0이 돼 reload count-1이 underflow하므로 단순 상수 변경을 하지 않는다.
01031900의108바이트 stub은 물리2.4G 선택에서5/10 요청을2로 매핑하고 `floor(C/500)`을 사용한다.
저장된2를 재설정하는 경로도 안전하게 처리하며 나머지 요청은 기존 계산을 유지한다.
주기 바이트20265를 바꾼 뒤 활동 timeout 환산0102a364를 다시 호출한다.
콜백·활동 코드는 이 주기 바이트를 공유하므로 순수 USB descriptor 패치와 다르다.

물리 스위치 SRAM201aa는 같은 패드의 전환 관찰에서2.4G=1, Bluetooth=0이었다.
시스템 clock MMIO가 직접 읽기에서FFFFFFFF였다는 결과를 실제 clock 주파수로 해석하지 않았다.

## 일정·활동 (최종 추가)

- callback0101dae4 진입을01031a00으로 바꾼다. 원래 prologue와 호출을 유지하며 tick2054c를 timer context24428에 저장한다.
- zero-delay 재등록 두 곳0101db1e/0101db40은01031a60으로 간다.
  선택 timer2441c, delay0, 물리 스위치201aa==1, period20265==2일 때만 시작 tick+1을 deadline으로 쓴다.
  나머지는 원래0102bcf0으로 간다. 작업이 끝난 tick 기준으로 추가 지연되는 부분을 줄이는 실험이다.
- 01020106의 활동 판정을01031ac0으로 보낸다. 기존 판정이 true이면 유지한다.
  그렇지 않을 때 변경된 packed axes20238가FFFFFFFF가 아니며 어느 바이트든119..135 밖이면 활동으로 인정한다.
  **변경 값**이 기준이다. 움직임 없이 스틱을 계속 고정한 모든 경우를 보장하는 수정이 아니며 출력 deadzone을 바꾸지 않는다.
- 첫 통합본의 RF flag20595 조건을 실제 물리 스위치 조건으로 바꾸는 비교에서는 평문4바이트만 달랐다.
- 뒤 스위치가2.4G이면 직접 USB에서도 일정 수정이 적용된다. Bluetooth 위치0은 원래 재등록을 쓴다.

timer context의 여유4바이트는16바이트 timer 간격과 참조 분석으로 추론했다.
모든 ROM 간접 접근이 없다는 전역 증명은 아니다. 타이머32비트 wrap 동작은 원본 그대로며 wrap 직전/직후 전체 동작은 검증하지 않았다.
활동 제한 재환산·타이머 처리·CPU 부하·진동/터보·배터리 소모에 대한 장기 시험이 필요하다.

## 수신기 패치

Full-Speed12Mbps의 활성 XInput IN descriptor만4→2로 바꿨다. `app.bin+10ee4`, JLFS app area 기준+10fa4다.
파일 data CRC/header CRC, 상위 area data CRC/header CRC 네 필드가 함께 바뀌어 DAT 총9바이트가 바뀐다.
보관된 공식4개 버전은 원본 exact roundtrip과 boot/file/area CRC를 확인했다.
배포 생성기는 정확한1.04를 검증하고 패치 후 중첩 CRC를 재검증하며 다른 파일 해시 보존을 확인한다.
감사 가능한 포맷 해독은 [receiver_format.py](../receiver_format.py)에 있다.
OUT8·대기 PID3109의 구성·부팅 영역·설정·페어링 키를 수정하는 패치가 아니다.

USB interval2는500회/초 요청 기회다. 같은 과거 상태를 받는 경우와 새 입력 생성500Hz는 다르다.
RF 패킷을500Hz로 확인한 것이 아니며 controller+receiver를 같이 바꿔도 태그 생성은 약289Hz였다.

## 업데이트 어댑터

수정 없는 제조사 x86 DLL의 `_updateGampeWithFile@4`(stdcall UTF-16 path)를 사용한다.
설정→ROM은 제조사의64바이트 `81 05 00 51 00 ...` 명령이다.6007은 설정,3208은 실제 USB boot PID다.
프리플라이트는 command8의 firmware type6007/6008을 확인한다. 컨트롤러는 command5로 고정 버전 레코드01017040의111을 확인한다.
장치 경로를 인수로 지정할 수 없는 제조사 API이므로8BitDo USB 장치를 한 대로 제한한다.

진행 getter는100을 반환하며 내부 값을0으로 바꾸므로 **최고값**을 보존한다.
`dll_errorUpdate`는 상태 조회가 아니라 중단/정리 함수이므로 폴링하지 않는다.
콜백을 루트로 유지하고 모델/PID 강제 변경 export를 호출하지 않는다.
공개 wrapper의 본체 기록 경로는 Controller B에서100%·전체 앱 읽기 일치·일반 입력을 확인했다.
v0.1.2는 공식 ZIP의 `data` 계층/초기 로그를 보존하며 누락 시 DLL 로드 전에 거부한다. 수신기 새 preflight 실물 시험은 별도 미확인이다.

## 충돌·불포함

alphaorderly의1세대 wake/remap 패치 범위01031838..0103192c는 주기 stub과 겹친다.
다른 커스텀 펌웨어에 이 패치를 덧씌우지 말고 정확한 공식 원본에서 다시 만든다.
Ultimate2C의 Telink 바이너리는 이식하지 않았으며 Switch2 wake/리매핑/절전 전면 해제/ROM 대기 제거를 포함하지 않는다.
