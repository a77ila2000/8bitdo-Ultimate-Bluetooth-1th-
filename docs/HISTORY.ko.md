# 조사 시작부터 최종 통합본까지

기록 기준: 2026-11-19~24, Asia/Seoul. 장치는 Controller A/B, Receiver A/B로 익명화했다.
최초 문제는 Bluetooth와2.4G 양쪽에서 조작 중 버벅임 후 표시등이 완전히 꺼지고 Home으로 다시 켜야 하는 현상이었다.
사용자가 처음 표현한 '과부하'는 원인으로 확정되지 않았다. 다음은 작업별 확인·정정·미확인을 보존한 이력이다.

## 1. 공식 펌웨어 확보와 깊이 비교 — 11월19~20일

- 정확한 원래 Ultimate Bluetooth 모델의 제조사 카탈로그에서 컨트롤러1.09/1.10/1.11, 수신기1.01~1.04를 확보했다.
- 공식1.11의 Switch2 지원 및1.10의2.4G 안정성 변경과 이 증상의 인과관계를 분리했다.
- 원래 펌웨어와 후속 세대의 모델·MCU·주소가 달라 후속 세대 이미지를 그대로 올리는 방법은 채택하지 않았다.
- 실제 Thumb 바이트 실행에서 ADC의 다섯 번째 정상 샘플이 실패/fallback으로 넘어가는 경계를 확인했다.
  세 버전 모두 동일했다. 이때 실패 카운터는 먼저0으로 지워지고 다시1이 되므로 이 사례만 반복해 여섯 실패 재시작에 도달한다는 초기 해석은 정정했다.
- 전부 비정상인 다섯 샘플이 반복되면 기존 누적/재시작 경로에 도달하지만 실제 장치에서 그 조건이 발생했다는 증거는 없었다.
- 배터리 경고 카운터가 예전 전체 바이트와 OR되어1,3,7,15,0x8f로 뛰고 정상 측정에서 감소하지 않는 동작을 세 버전에서 확인했다.
  직접 호출은 경고 LED/백분율/출력 플래그이며 즉시 저전압 차단이라는 해석은 하지 않았다.
- 대기·활동·연결 watchdog·종료 루틴 13개는 정규화한 상위 흐름이 같았으나 모든 callee가 동일하다고 주장하지 않았다.
  v1.11의 watchdog SRAM 참조 변경 등 실제 차이를 따로 보존했다.
- 수신기에는 같은 ADC 오류를 발견했다는 근거가 없었다. 최초 안정성 수정 단계에서 수신기를 함께 바꿀 필요는 입증하지 못했다.

## 2. 첫 수정 업데이트 — 11월20일

1. 장치 네 개를 한 번에 검색하던 제조사 updater가 종료돼 한 대씩 분리했다.
2. 공식 updater2.52의 작업 디렉터리를 프로그램 폴더로 잡은 뒤 정상 검색/업데이트를 확인했다.
   이 결과를 모든 시작 오류의 일반 원인으로 확대하지 않았다.
3. Controller A에 공식1.11을 먼저 재설치해100% 및 전체 기록 완료를 확인했다.
4. 제조사의 수정 없는 DLL과 로컬 파일 업데이트 export를 사용해 ADC+배터리 경고 카운터 시험본을 기록했다.
5. USB를 다시 꽂아 같은 물리 장치의 일반 입력 복귀를 확인한 뒤 Controller B에도 같은 수정본을 적용했다.
6. 각55초 범위의 USB 검사에서 방향키·ABXY·스틱 변화를 확인했다. 사용자는 두 패드의 셋톱 홈 입력도 확인했다.
7. Receiver A/B는 둘 다 공식1.04였다. 이 시점에는 수신기에 쓰지 않았다.

첫 기록 DAT는 `78d7364a…198b0b7`이다. 앱 버전·모델·목적 주소를 유지해 화면은 계속1.11로 보인다.
이때는 전체 플래시 재읽기를 하지 않았으며 진행100%와 정상 부팅을 전체 readback 증거로 취급하지 않았다.
셋톱 후속 조회에서 패드가 다시 대기 형태였던 관찰과 사용자의 앞선 홈 동작 확인을 같은 시각의 증거로 합치지 않았다.

**PID 정정:** USB6007은 설정 통신이며 컨트롤러와 수신기 모두 사용할 수 있다.
실제 ROM updater는3208이고, 펌웨어 헤더6007(컨트롤러)/6008(수신기)과 다르다.
초기 파일명에 'boot'가 들어간6007 조회를 부트 복구 성공으로 해석한 설명을 정정했다.

## 3. PC 반복 입력과 속도 측정의 한계

- 사용자가 수신기를 PC에 연결했으므로 셋톱이 아닌 Windows XInput을 기록하는 것으로 수정했다.
- 임의의 버튼·스틱 조작2분 동안 Windows 연결 해제가 없었다. 사용자는 화면상 동작 기준이 없어 입력 누락을 판단할 수 없었다.
- 실제 누름 횟수와 시점을 독립 측정하지 않았으므로 무누락·절대 지연 검증으로 결론 내리지 않았다.
- 60초 수동 스틱 시험의 실제 변화 구간은8.852초,2111개 변화로 약238.36Hz였다.
  중앙값 약4.001ms를 순정 대비 향상이나 RF 정확한 주기로 해석하지 않았다.
- PC가 같은 상태를 자주 조회하거나 패킷 번호가 바뀌는 것과 컨트롤러의 실제 새 입력 생성은 다르므로 자동 source 태그 시험으로 전환했다.

## 4. 2.4G 500Hz 목표의 주기 시험 — 11월24일

- 수신기는 Full-Speed12Mbps였고 활성 XInput IN interval4, OUT8이었다.
- Receiver A만 공식1.04 재설치 경로를 확인한 뒤 IN4→2와 중첩 CRC를 고친 시험본을 기록했다.
  부팅 영역·설정·다른 파일·OUT interval·대기 구성은 변경하지 않았다. Receiver B는 그대로 유지했다.
- 컨트롤러 setter는 기존 `clock/200 * uint8(period/5)`였다. 단순5→2는 나눗셈 결과0 및 reload underflow가 돼 채택하지 않았다.
- 2.4G 물리 스위치 값0x201aa==1, Bluetooth 위치0을 실제 전환으로 확인했다.
- Controller A에 올바른 clock/500 계산과 저장 주기2, 활동 제한시간 재계산을 포함한 시험본을 적용했다.
  실제 주기 바이트2를 읽었다. MMIO 읽기의FFFFFFFF를 실제 클럭값으로 쓰지는 않았다.
- 첫 수신기 단독/조합 수동 시험은 중앙값5.315/5.803ms 등으로 변동이 있었으며500Hz 증거가 아니었다.

## 5. 공개 GitHub 구현 비교

정확한 고정 커밋은 [SOURCES](SOURCES.md)와 [자료](../evidence/source-review.json)에 있다.

- alphaorderly 및 gomezluisj의 정확한1세대 프로젝트는 Switch2 깨우기·재연결·리매핑 작업이었다.
  2.4G 속도 수정으로 인용하지 않았다. 전자의 패치 범위가 기존01031900 주기 코드와 겹쳐 그대로 합치지 않았다.
- Ultimate2C Wireless용 toolkit은 Telink 계열로 주소/명령이 달랐다. 빠른 입력/활동 판정 아이디어를 검토했지만 다른 기종 코드와 펌웨어를 이식하지 않았다.
- 1세대의 자체 코드에서 스틱 변경값 활동 인정과 입력 callback의 재등록 시점을 별도로 작성했다.
- XIP 앱 전체 재읽기 개념을 검증에 사용했다. Switch2 wake 코드는 설치하지 않았다.

## 6. 통합 일정·활동 시험 및 자동 계측

첫 통합본은 ADC·배터리·2ms에 활동 판정과 callback 시작 tick 기준 일정을 추가했다.
당시 후보 RF flag0x20595의 실제 활성 의미는 확인되지 않았으며 USB에서는0이었다.
첫 통합본 앱 전체 재읽기 일치와 이 미확인 조건을 구분해 기록했다.

자동 계측 첫 버전은 특정 report5 생성 경로를 태그했으나 수신기에 태그가 안 보여 속도 결과에서 제외했다.
다음 버전은 공통 axes getter와 snapshot에 순번/tick을 넣었고 USB에서 먼저 확인했다.
완전 전원 재시작 후 수신기에서도 태그를 받았다. 실행 제한시간이 이미 끝난 상태를 RF 실패로 오판하지 않았다.

16단계 교정값으로12비트 순번을 복원하고 트리거 바이트 순서 후보를 비교했다.
source500/수신250과 source250/수신250 합성 자료를 구별하는 해독기 검사를 했다.

- 이전 통합본: 유효46.514초, 관측11385개, source11384 증가,244.745Hz.
- 실제 물리 스위치 조건으로 수정: 유효54.410초, 관측15724개, source15729 증가,289.081Hz.
- 비교 진단본 사이 일반 코드 차이는 네 바이트의 물리 스위치 조건/포인터였다. 진단 태그 코드는 같았다.
- source 태그가 증가한 지점은 보고서 처리 경로이며 RF 전송 성공/ACK의 독립 카운터가 아니다.
- 약18.12% 차이지만 무작위 반복 A/B는 아니고 PC 조회 공백도 있어6개 번호 공백을 RF 손실로 확정하지 않았다.

## 7. USB 복구·ROM 검토·최종 일반본 복귀

- USB 재연결 중 장치 설명자 요청 실패를 관찰했다. 해당 상태에서 추가 플래시 쓰기는 시작하지 않았다.
- Windows PnP 재시작은 접근 거부였다. 완전 종료 후 L/R을 누른 USB 연결로3208을 회복했다.
- 부트 command8의 모델6007 및 고정 버전 레코드111/beta0을 CRC와 함께 확인했다.
  updater의 일시적 'Version0' 표기를 실제 펌웨어 버전으로 해석하지 않았다.
- ROM의 작은 대기 함수0x4238은 클럭 분주 기반 루프였다. 인수2를2ms라 단정하거나 정착 대기를 제거하지 않았다.
  전체 하위 루프/실측 단위는 미확인이었다. 버튼 접점 지연 개선량도 미확인이다.
- 최종 일반 `controller-enhanced` DAT 기록100% 후 앱105472바이트 전체를 재읽어 일치를 확인했다.
- 뒤쪽512바이트는 FF여서 임시 자동 태그 코드가 남지 않았음을 확인했다.
- 정상 모드 전환 후15초간 수신기에서 A11/B9/X7/Y8 눌림·해제, 방향키·스틱 양/음 값을 받았다.
  종료 시 중립, 관측 중 연결 해제 없음이었다. 실제 누름 횟수의 독립 기준은 없었다.
- 수신기는 최종 조회에서도 Full-Speed IN2/OUT8이었다.

## 8. 공개 배포 포장 — 11월24일

개인 장치 번호·PC 경로·계정/네트워크 정보·개인 원시 덤프를 제외했다.
이력의 세 컨트롤러 변형과 수신기 변형, 공식 원복 파일을 정확히 재현하는 레시피/생성기를 공개했다.
새 공식 다운로드부터 생성한 여섯 DAT가 보관된 실제 기록 파일과 같은 SHA-256임을 확인했다.
Windows 바이너리와 제조사 DLL 호출 어댑터를 소스와 함께 제공한다.
이 공개 어댑터의 코드/거부/로드 검사는 기존 개인용 경로의 실제 기록 증거와 별개다.
모든 수정이 장시간 게임·충전·진동·터보·양쪽 패드/수신기 동시 사용에서 검증된 것은 아니다.
